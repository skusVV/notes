Notes Bot Architecture

Overview

The bot receives a Telegram message, decides what kind of thing it is (a note, a reminder, a symptom, a question, and so on), and replies describing what it understood. It calls Google's Gemini model twice per message at most - once to turn speech into text, once to classify the text. Until recently it kept no memory between messages; now a resolved reminder is written to Firestore as one or more independent notifications - "the evening before and the morning of" is two - each delivered on schedule by a Cloud Scheduler sweep, and acknowledged or snoozed with a button tap on its own. A reminder can also repeat - a birthday, "every Monday at 8am" - in which case it never expires and the sweep re-arms the next occurrence itself. It has also started remembering people: a reminder that names somebody it does not know draws exactly one follow-up question, and whatever you answer is kept as that person's notes. And a stray thought that is not a reminder, a symptom, a question, a correction, or a fact about a person is now kept too, as a plain note - no trigger word needed. A health complaint - "болить голова" - is now filed as well, as a symptom: its type normalised so the same ache counts the same however you word it, and a severity number kept only when you actually give one.

Persistence and delivery have begun, now scale to several nudges per reminder, and can repeat forever. Reminders with a clear date and time are stored in Firestore as one or more independent notifications documents - one appointment can carry an evening-before nudge and a morning-of nudge, each claimed, delivered, acked and snoozed on its own by a Cloud Scheduler sweep with OK / +1h / Tomorrow buttons (spec 0003-reminder-delivery, evolved by spec 0004-multiple-notify-times). A reminder that explicitly repeats - yearly, weekly, monthly or daily - is stored as a wall-clock rule instead of a fixed instant, never expires, and the sweep arms its next occurrence the moment the current one fires (spec 0005-recurring-reminders). A reminder that names a person the bot does not know yet also triggers one question about them, whose answer becomes an actors record - the first thing here stored about somebody other than a time (spec 0006-actor-capture). A stray thought the bot cannot place - anything it classifies note or other - is now written to a notes store rather than only previewed, so an off-hand observation is kept without any trigger word (spec 0007-notes-capture). A health complaint the bot classifies symptom is now written to a symptoms store too, its type normalised to a shared slug so the same ache counts the same across wordings and its severity kept only when the user actually stated a number - never inferred from a word like "сильно" - which is what makes a later "how often" signal possible at all (spec 0011-symptoms-capture). The remaining intents (question, correction) are still only previewed, so a reply that did not store everything it acted on still ends with a notice saying so. The Planned: Memory Layer section below is the rest of the phase: the entries capture log and Vertex embeddings turn these replies into a searchable, remembered history.

System Map

Who talks to whom. One Cloud Function sits in the middle: Telegram sends it updates over a webhook, it calls Vertex AI (Google's hosted Gemini models) for both speech-to-text and classification, it writes reminders, their independent notification records, the people it has been told about, stray thoughts kept as notes and the health symptoms it is told about to Firestore, and a Cloud Scheduler cron now ticks the function's own /sweep endpoint to deliver due notifications. Cloud Build redeploys the whole thing automatically on every push. The one remaining amber box (Vertex embeddings) is not built yet - it shows where the rest of the planned memory layer plugs in.

Request Flow

What happens to one incoming message, in order. Two steps in this chain are load-bearing precisely because of their position, not just their logic - moving either one down the list would change what strangers can do to this bot.

Classification

One Gemini call per message returns a list of intents - a list, not a single label, because "I have a headache and remind me to call the doctor" is genuinely two things. A confidence score on each item decides whether the bot acts quietly, acts but shows its interpretation, or asks instead of guessing.

Three defensive rules in classifier.service.ts keep a bad model reply from ever becoming a crash: an unknown intent is dropped, a payload that fails validation (a reminder with no title) has its confidence forced below the "ask" threshold instead of being repaired, and an absent field (severity, lead time) is never guessed - a fabricated number would quietly corrupt every later average.

Reminders: resolving a time without inventing one

Spec 0002 added a fourth guard for reminders. The classifier is now handed the current local time (the new now field on ClassifierContext) and told to resolve relative speech - "Thursday at 12", "next Thursday", "the 25th" - into an ISO instant carrying the user's offset. It also returns a required hasTimeOfDay flag: true only when the message stated an explicit clock time, false for a bare date or weekday.

The invent-nothing rule. When hasTimeOfDay is false, the code forces the item's confidence below CONFIDENCE_ASK, so the bot asks instead of filing a guessed time. This is a deterministic backstop: a model that copies the hour from "now" produces a valid-looking instant that normalizeEventAt alone cannot catch, so a reminder whose time of day was never actually spoken is treated as unresolved even when its eventAt parses.

Notify times: one event, several independent nudges

Spec 0004 separates when the thing happens from when to nudge about it. A reminder keeps exactly one eventAt; the classifier's new notifyAt is an array - one entry per requested nudge, so "the evening before and the morning of" is two entries, not one. Each entry is either an explicit ISO instant with an offset or one of five fixed relative keywords - morning_of, evening_of, morning_before, evening_before, at_event. notify-times.ts resolves each keyword against eventAt - "morning" is a fixed 09:00 local, "evening" 19:00 local, both fixed for v1 - then de-duplicates, sorts the results ascending, and drops anything at or before "now" (it would otherwise fire on the very next sweep instead of when it was meant to). A message that names no notify time at all still gets exactly one notification, at eventAt - the 0002/0003 behaviour, unchanged.

Notifications, not the reminder, are the delivery source of truth. RemindersService.create writes the reminder document once, plus one notifications/{autoId} document per resolved instant - each with its own status, claimed, sent, acked and snoozed independently of the others. The reminder's own status field is written once at creation and never changes again; see the notifications record in the Planned: Memory Layer data model below for what moved off the reminder document.

Recurrence: a wall-clock rule, not a stored instant

Spec 0005 lets a reminder repeat - yearly (a birthday), weekly, monthly, or daily. The classifier's recurrence field is now a structured object (freq, plus whichever of month / day / weekday the frequency needs, plus an optional atLocal), emitted only when the message itself says the thing repeats - a routine-sounding message ("I usually take my vitamins in the morning") stays a one-off. recurrence.ts's normalizeRecurrence then validates it exactly like notify-times.ts validates notify keywords: a weekly rule with no weekday, a yearly rule with no month, or "31 June" are all dropped rather than repaired, because an invented rule fires forever at a time nobody asked for. A birthday or anniversary is filed as a reminder with a recurrence, not as actor_info - see the Classification table above.

Stored as local time plus timezone, never as a UTC instant. "09:00 on June 12" is 06:00 UTC in summer and 07:00 UTC in winter in Europe/Kyiv, so a rule saved as one UTC instant would silently drift by an hour twice a year. Recurrence instead carries atLocal ('HH:mm') and its own timezone, and nextOccurrence / nextOccurrenceAfter resolve each occurrence's offset from that occurrence's own date - the same rule resolves to +03:00 in June and +02:00 in December. The default time of day, 09:00 local, is the one thing the code fills in (a birthday named no clock time); everything else the model did not state is dropped, not guessed.

Never expires - and "never" is expressed by leaving the field out, not by a far-future date. A recurring reminder and its one scheduled notification are written with no expireAt key at all, because Firestore's TTL policy only reaps documents where that field is present; a far-future timestamp would eventually arrive and delete a birthday that is supposed to outlive it. The one path that could have undone this quietly is +1h / Tomorrow snooze - snoozeNotification now takes a recurring flag (sourced from OwnedNotification.recurring) and skips writing expireAt when it is set.

The sweep rolls a recurring reminder forward the moment it delivers the current occurrence - keyed on the claim, not on a successful send. sweeper.service.ts's transactional scheduled → sent claim already fires exactly once per occurrence; right after a successful claim it calls RemindersService.enqueueNextOccurrence, which resolves the occurrence after the one just fired (never from "now" - a tick runs up to one look-ahead interval early, so "at or after now" would re-arm the occurrence that just fired) and writes it inside a transaction that refuses to run if the reminder already has a scheduled notification. That guard is what keeps a retried Cloud Scheduler tick from arming two. Rolling forward on the claim rather than after the Telegram send succeeds is deliberate: skipping it after a failed send would leave the reminder with zero scheduled notifications - it would silently stop recurring, which is worse than one missed nudge.

Mentions: who the message was about

The classifier has always returned a mentions array alongside the intents. Spec 0006 is the first thing to use it, and changed what goes in it: a mention is now written in its base dictionary form - nominative case, no inflection - so "привітати Антона", "подзвонити Антону" and "Антон" all come back as Антон. Ukrainian and Russian inflect a name by grammatical case, so surface forms would otherwise never match each other and the bot would ask about the same person forever. Nothing is lost by normalising: the message itself is still kept verbatim in the reminder's originalText. The schema also narrows who counts - a proper name or a personal/relational reference ("my wife", "сусідка"), never a generic professional role (a doctor, a taxi driver, a cashier), because that is a different unnamed person every time and asking about them is noise.

The prompt asks; the code enforces. ClassifierContext now carries declinedMentions next to knownActors, and both are rendered into the prompt as "never list these again" sections - but that is only an optimisation. The rule that the bot never asks twice is enforced in actors.service.ts's resolve, which compares the mention case-insensitively against every known actor's name and aliases and against the declined list, and returns known / declined / new. Correctness never depends on the model obeying its instructions.

Firestore setup (Console, one-time). Create two Native-mode databases in europe-west1 (permanent, cannot be changed later): (default) for production and test for the isolated test function. On each, add three Time-to-live policies: timestamp field expireAt on collection group reminders and (spec 0004) on collection group notifications - Firestore does not cascade a delete into subcollections, so a reaped reminder would otherwise leave its notifications behind, still due - plus (spec 0006) timestamp field expiresAt on collection group pending, which holds the single open "who is this person?" question per chat. That third one is cleanup only, never correctness: the code checks expiresAt itself before honouring a question, so a late TTL run leaves a dead document lying around but can never make an expired question answerable. Spec 0006 needs no new composite index - its reads are a document get and a single-field orderBy('createdAt') on a subcollection, both automatically indexed. Also add a composite index on the notifications collection group (query scope Collection group; status Asc, at Asc) that the sweep's findDue query needs since 0004 - skipping it fails with a FAILED_PRECONDITION carrying a Console link that creates exactly this index (this is exactly what blocked 0004's first verification attempt). Keep the older reminders (status Asc, remindAt Asc) index from spec 0003 until the one-time legacy backfill finishes (the sweep logs Backfilled 0 legacy reminder(s) once it's done), then it can be deleted. The runtime compute service account needs roles/datastore.user (above), which already covers both collections.

Recurring reminders need no Console change (spec 0005). A repeating reminder - a birthday, "every Monday at 8am" - and its notification are written with no expireAt field at all. The TTL policy only deletes documents where its timestamp field is present, so leaving the field out is what makes "never expires" work with nothing extra to configure - not a far-future date, which would eventually arrive and delete a birthday that is supposed to outlive it.

Cloud Scheduler setup (Console, one-time). Create a job that POSTs to the function's own /sweep endpoint every REMINDER_SWEEP_INTERVAL_MINUTES (default */30 * * * *, timezone Europe/Kyiv), with a header X-Sweep-Secret carrying the REMINDER_SWEEP_SECRET value - the same shared-secret pattern the Telegram webhook uses. See README.md step 8. Keep the cron frequency and the env var equal, or reminders drift late or get swept twice.

Deploy Pipeline

One push, one build step, one always-on gen2 function. There is no separate CI step and no Docker build - the Google Node.js buildpack compiles TypeScript for you.

Delivery Workflow

Non-trivial changes go through a spec, not a direct edit. One agent implements, a different agent verifies against the live isolated test function - an agent grading its own work is biased toward "it works," so the check is a fresh pair of eyes. Once a spec is READY, /implement-spec runs the whole chain hands-off: build, verify, refresh this map, merge to main, and push - which deploys to production.

Planned: Memory Layer reminders, actors, notes + symptoms live the rest planned

The bot stops replying and starts remembering. Every message becomes an immutable record before any model looks at it - interpretation can be wrong and re-run later; the words themselves never are. Full reasoning: docs/architecture.md.

The one rule: capture is sacred, interpretation is disposable. A model that misreads "remind me about the dentist" still leaves the original words intact - you lose a reminder, not a memory.

Build order

0

Persistence & capture

Firestore, entries keyed on update_id, a user timezone. No intelligence at all.

Why first: de-risks everything above it - and it's the phase where sacred-capture either gets built in or gets lost.

1

Classifier & confirmations

The intent array, the "other" ladder, visible confirmations, corrections, a fixture test of ~30 real messages.

Shipped out of order, on request: the classifier and per-intent branching already exist today, built before phase 0 so routing could be judged against real messages first. Persistence, correction, question, and inline keyboards still wait on phase 0.

2

Reminders

Capture and store first (resolve a time, write the record), then the Scheduler sweeper, delivery, snooze / ack buttons, multiple notify times and recurrence.

Fully shipped (specs 0002-0005): reminders resolve to a concrete instant, persist to Firestore as one or more independent notifications, and are delivered by a Cloud Scheduler sweep with OK / +1h / Tomorrow buttons acting on each one. A reminder can also repeat - yearly, weekly, monthly, daily - stored as a wall-clock rule that never expires and rolls itself forward on delivery (0005, verified, about to merge). First feature needing both stored state and a clock; now the most complete phase on this page.

3

Symptoms partly live

Normalized vocabulary, plus a doctor-visit summary view.

Capture slice shipped (spec 0011): a symptom is now stored with a normalized type slug, severity kept only when a number was stated (never inferred), and a present-tense complaint dated to now - reusing the classify-confirm-store path from phase 2 with no new infrastructure, exactly as predicted. The known-slug vocabulary is fed back into the classifier so the same ache lands on one slug across wordings, which is what a later count depends on. Still deferred: the insight / pattern-noticing layer (spotting a cluster of headaches and nudging), the doctor-visit summary, and any retrieval - all of which need history and aggregation (phase 4).

4

Recall

Structured queries first, then embeddings, the vector index, and hybrid keyword retrieval.

Why here: semantic search over an empty corpus proves nothing - by now there's real data.

5

Actors partly live

Detection, the ask, aliases, then a backfill pass over existing entries.

Why last: the only feature that improves by arriving late - it can retro-label months of history in one pass. Built early anyway, as a slice (spec 0006): detection, the one-question ask, the decline, and verbatim capture are live now, scoped to the reminder intent. The retro-label argument only bites if there is history to relabel, and the generic entries capture log of phase 0 does not exist yet - so nothing was lost. What is still deferred is the labelling half: relation, richer aliases, and the backfill pass.
